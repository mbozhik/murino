## Резервный снимок DNS `malakhov.group`

Снимок сделан 31 июля 2026 года перед переключением домена на DNS-серверы хостинга REG.RU.

| Имя | Тип | TTL | Значение |
| --- | --- | ---: | --- |
| `malakhov.group` | NS | 21600 | `ns1.reg.ru` |
| `malakhov.group` | NS | 21600 | `ns2.reg.ru` |
| `malakhov.group` | A | 21600 | `147.45.245.24` |
| `www.malakhov.group` | A | 21600 | `147.45.245.24` |

На момент снимка публичные записи `MX`, `TXT`, `CAA` и `AAAA` отсутствовали.

Для отката нужно вернуть `ns1.reg.ru` и `ns2.reg.ru`, затем восстановить обе A-записи на `147.45.245.24`. Распространение изменений DNS может занять до 24 часов.

31 июля 2026 года переключение подтверждено и применено в личном кабинете: для `malakhov.group` установлены `ns1.hosting.reg.ru` и `ns2.hosting.reg.ru`. Распространение оказалось неоднородным: разные проверки Google Public DNS, Cloudflare DNS и локального резолвера в течение дня возвращали разные комбинации старых/новых NS и A-записей. В 14:00 MSK Google DoH ещё показывал старые `ns1.reg.ru` / `ns2.reg.ru`, а A уже показывал `37.140.192.23`; локальный HTTP-маршрут всё ещё попадал на `147.45.245.24`. До истечения старого TTL это ожидаемо, поэтому окончательная проверка выполняется повторно после стабилизации.

## Подготовленное состояние хостинга

- Для передачи файлов установлен `lftp 4.9.3`; подключение по FTPS проверено.
- Пароль FTP не хранится в репозитории или конфигурационных файлах.
- SFTP для этого аккаунта не предоставляется; обычный незашифрованный FTP не используется.
- В ISPmanager `malakhov.group` и `www.malakhov.group` вынесены в отдельный redirect-сайт без копии файлов; оба имени перенаправляются на `https://malakhovcorp.ru/`.
- Для всех трёх проектов выпущены сертификаты Let's Encrypt, включены gzip и перенаправление HTTP → HTTPS.
- Для всех трёх сайтов включено кеширование; HSTS пока не включён до завершения переноса и проверки отката.
- 31 июля 2026 года production-сборки всех трёх проектов загружены в соответствующие каталоги; результаты и проверки перечислены ниже.

## Первая production-публикация

Публикация выполнена 31 июля 2026 года через FTPS с помощью `lftp`. Исходники на хостинг не передавались — только готовые статические артефакты.

| Проект | Команда сборки | Публикуемый каталог | Результат |
| --- | --- | --- | --- |
| Murino | `bun run build` | `/Users/bozzhik/code/murino/out` | Next.js static export, 66 файлов |
| Maraku | `pnpm run build` | `/Users/bozzhik/code/maraku/dist` | Vite build, 37 файлов |
| Wife | `bun run build` | `/Users/bozzhik/code/wife-website/dist` | Vite build, 11 файлов |

Для Murino в `next.config.mjs` включены `output: 'export'`, `trailingSlash: true` и `images.unoptimized: true`. Это обязательная конфигурация для обычного статического Host-Lite без Next.js runtime. Сборка содержит `/index.html` и `/metro/index.html`.

Перед публикацией все три исходных web-root были скачаны в:

```text
/tmp/reg-hosting-backup-20260731-Ur4Gwm
```

Перед финальной SEO-публикацией создана дополнительная полная копия:

```text
/tmp/reg-hosting-final-backup-20260731-gqYpiG
```

Обе копии находятся во временном каталоге macOS и не считаются долговременным архивом.

Первая копия занимает 2,2 МБ и содержит по одному исходному файлу-заглушке `index.html` для каждого сайта. Все три файла имели размер 768285 байт и одинаковый SHA-256:

```text
e479bb91cec74f999fd38c628f8edb3472f51489bd5cc7e277b56c6969d83583
```

Финальная копия занимает 17 МБ и содержит полный снимок сайтов непосредственно перед SEO-публикацией: Murino — 64 файла, Maraku — 35, Wife — 9 (всего 108 файлов). Это резервная копия готовых файлов на хостинге, а не исходного кода, DNS-записей, базы данных или старого VPS.

Каталоги загружались без `--delete`: существующий `index.html` заменён, новые файлы добавлены, произвольные старые файлы не удалялись. После загрузки каждый удалённый каталог был скачан обратно в `/tmp/reg-hosting-verify-20260731-rD3zBm` и сравнен с локальной сборкой через `diff -qr`:

- Wife: 9 локальных / 9 удалённых файлов, различий нет;
- Maraku: 35 локальных / 35 удалённых файлов, различий нет;
- Murino: 64 локальных / 64 удалённых файла, различий нет.

- Все восемь имён резолвятся в Host-Lite: A `37.140.192.23`, AAAA `2a00:f940:2:2:1:1:0:115`.
- SHA-256 публичного `index.html` каждого проекта совпадает с локальной production-сборкой.

- `robots.txt` и `sitemap.xml` каждого проекта возвращают HTTP 200; у `malakhov.group` эти файлы перенаправляются на соответствующие файлы `malakhovcorp.ru`.
- `/metro/` Murino возвращает HTTP 200 с `noindex, nofollow`, после загрузки страницы выполняется перенаправление на карту.
- Сертификат Maraku покрывает четыре имени; сертификаты Murino и Wife покрывают apex и `www`. Все сертификаты действуют до 29 октября 2026 года.

### Повторяемая ручная публикация

Пароль вводится интерактивно и нигде не сохраняется:

```bash
lftp -u u3594311 ftp://37.140.192.23
```

Внутри `lftp`:

```text
set ftp:ssl-force true
set ftp:ssl-protect-data true
set ssl:verify-certificate no

mirror /www/<domain> /absolute/path/to/backup/<domain>
mirror --reverse /absolute/path/to/build /www/<domain>
```

Отключение автоматической проверки сертификата здесь допустимо только для этого проверенного сервера: цепочка FTPS у REG.RU неполная, а сертификат был отдельно проверен перед первым подключением. Перед удалением удалённых файлов необходимо выполнить новую резервную копию и отдельную проверку; текущая процедура намеренно ничего лишнего не удаляет.

- Murino, Maraku и Wife полностью обслуживаются Host-Lite и готовы к обычной работе.
- Канонические адреса: `https://murino-arena.ru/`, `https://malakhovcorp.ru/`, `https://bestwifenastya.ru/`.
- `malakhov.group` подключён как дополнительный домен Maraku и склеен с `malakhovcorp.ru` серверным 301 без дублирования production-файлов.
- HSTS намеренно не включён: HTTPS уже принудителен, а необратимую на время действия заголовка политику разумно включать отдельно после периода стабильной эксплуатации.
- Локальный VPN может продолжать показывать устаревший маршрут; для контрольной проверки использовать независимую сеть или VPS.

## Правила будущего переноса

1. Не хранить FTP-пароль в Git, shell history или скриптах.
2. Перед каждой публикацией сохранить удалённую копию текущего каталога сайта.
3. Сначала выполнять dry-run синхронизации без удаления удалённых файлов.
4. Загружать только готовый статический результат сборки, а не исходники проекта.
5. До переключения DNS проверить сайт через безопасный preview-маршрут с правильными Host и SNI.
6. После переключения проверить HTTP → HTTPS, сертификат, apex и `www`, основные страницы и статические ресурсы.
7. Проверить canonical, `robots.txt`, `sitemap.xml` и отсутствие индексируемых дублей на дополнительных доменах.
8. Удаление старых файлов разрешать отдельно и только после проверки резервной копии.
